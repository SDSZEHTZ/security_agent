## 2. 从规划到真实工具的完整数据流

```text
User Goal
  → Planner（可提建议，不持有执行权限）
  → PlanProposal / PlannedTask.arguments
  → PlanValidator（阶段、能力、范围、依赖等检查）
  → PlanCompiler（分配 T1/T2...，复制 arguments）
  → Scheduler（READY 不等于并行）
  → Supervisor（Schema/Workflow/Capability/Policy/Scope/HITL）
  → ApprovalSnapshot（不可变请求快照）
  → ToolContext（Runtime 创建，填授权源码根目录/Origin）
  → Agent.run(snapshot, tool_context)
  → ToolExecutor（Agent+Action→Tool Allowlist、参数模型校验）
  → ToolRegistry / Tool.execute（有边界的真实 I/O）
  → ToolResult（SUCCESS 或 ERROR）
  → Observation（客观结果）
  → StateManager（Task 状态、必要时 Evidence/Finding）
```

**重要边界：** Schema 合法不代表可执行；Agent Capability 不代表有工具使用权；Tool SUCCESS 不等于漏洞存在；HTTP 200/500 不是漏洞证明。Supervisor 和 ToolExecutor 分别负责 Task 安全检查和 Tool 权限检查，两层不可互相取代。

## 3. 第一组：可信请求与上下文

### 3.1 `models/request.py`、`runtime/workflow.py`、`runtime/policy.py`

已存在合法 Action `check_http_baseline`，仅在 VERIFY 阶段开放，Policy 默认 ALLOW。ALLOW 基于工具限制：只接受 Runtime 的固定 Origin、GET/HEAD、相对路径，禁止代理和自动重定向，并设超时与响应大小上限。

`Action = Literal[...]` 是 Python 的类型约束；Pydantic 根据它拒绝不在候选集合内的 Action。`Literal` 不负责权限：参数类型合法仍然需要经过 Workflow/Policy/Scope 检查。

### 3.2 `state.py`、`models/tool.py`

`state.target` 表示授权源码项目根目录，例如 `./demo_app`；`state.authorized_origin` 表示授权 HTTP Origin，例如 `http://127.0.0.1:5000`。两者属于不同资源类型，不能拿 `target` 直接当网络 URL。

可信上下文模型：

```python
class ToolContext(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)
    task_id: str
    agent: str
    action: Action
    authorized_root: str | None = None
    authorized_origin: str | None = None
```

`frozen=True` 禁止普通字段重新赋值；`extra='forbid'` 阻止未声明字段。因为此处授权值是字符串，模型的冻结能阻止字段的直接变更，但这不是对执行任意 Python Agent 的沙箱隔离。

### 3.3 `runtime/supervisor.py`

Supervisor 已存在核心方法：

```python
def _build_tool_context(self, task, state):
    return ToolContext(
        task_id=task.id,
        agent=task.agent,
        action=task.action,
        authorized_root=state.target,
        authorized_origin=getattr(state, "authorized_origin", None),
    )
```

关键点在于 `authorized_root` 和 `authorized_origin` **来自 State，不来自 `task.arguments`**。即使 LLM 在参数中塞入假的授权目录或者外部主机，也不能覆写上下文。

执行时统一：

```python
result = agent_info["instance"].run(
    execution_task,
    tool_context,
)
```

没有 `except TypeError: agent.run(task)` 这种旧接口回退；否则 Agent 内部本身抛出的 TypeError 可能触发第二次执行，引入重复副作用。

## 4. 第二组：Tool Registry、ToolExecutor 和 Agent

### 4.1 `main.py` 依赖注入

`build_tool_executor()` 已注册三种工具：`ReadSourceTool`、`SearchCodeTool`、`ControlledHttpCheckTool`，随后为 `(agent, action)` 配置工具允许集。

```python
("CodeAnalysisAgent", "analyze_code") → {"search_code", "read_source"}
("CodeAnalysisAgent", "read_file")     → {"read_source"}
("VerificationAgent", "check_http_baseline") → {"controlled_http_check"}
```

其他组合默认空权限。`build_registry(tool_executor)` 将**同一个** ToolExecutor 注入两个 Agent。这个思路叫依赖注入（Dependency Injection）：Agent 不自行构造全局工具，也不拿到完整 State。

### 4.2 `agents/code_analysis.py`

`run()` 根据 `task.action` 分流：

- `analyze_code`：从快照取 `query` 和可选 `max_matches`，调用 `search_code`。
- `read_file`：取 `path`，调用 `read_source`。
- 其他 Action：返回 FAILED Observation，不能偷用未授权工具。

本版 `search_code` 命中 `cursor.execute(query)` 只意味着发现字面字符串，不意味着输入可控、执行到达或存在 SQL 注入。因此**不得再生成硬编码的 `potential_findings=['SQL Injection']`**。

`task.arguments` 是通过 `ApprovalSnapshot.arguments` 属性从规范化 JSON 反序列化的新字典，因此不会直接共享原始 Task 的可变参数对象。

### 4.3 `agents/verification.py`：本轮修正

原 ZIP 的 baseline 输出是把 Tool 返回字段直接铺到 `Observation.data` 顶层。本轮按已有规划调整为：

```python
return self._observation(task, "SUCCESS", {
    "tool_name": tool_name,
    "http_baseline": result.data,
})
```

这使调用方通过 `observation.data["http_baseline"]["status_code"]` 读取 HTTP 基线结果。`EvidenceExtractor` 仍然只识别已有的 `verify_sqli` / `verify_ssrf` 教学验证动作，baseline 不产生 SQLi/SSRF Evidence。

保留的 `verify_sqli`/`verify_ssrf` 和 `ReportAgent` **仍是教学模拟**，不能把对应的模拟 Evidence 当成生产环境真实漏洞结论。

### 4.4 错误传播

典型链路：

```text
Tool permission/arguments denied
  → Agent 把拒绝转换为 FAILED Observation
Tool.execute 出现异常
  → ToolExecutor 返回 ToolResult(status="ERROR")
  → Agent 转换为 FAILED Observation
  → Supervisor 保存 Observation，并把 Task 更新为 FAILED
```

Task FAILED 表示执行路径失败；Task BLOCKED 表示在安全校验、依赖等条件下无法执行；Finding 的 POTENTIAL/CONFIRMED 等状态与两者不是同一枚举。

## 5. 第三组：真实工具的安全性

### `read_source`

使用 `Path.resolve(strict=True)` 和 `relative_to(root)` 确保真实文件路径仍处于授权根目录；限制绝对路径、`..`、越界软链接、敏感文件名、扩展名和最大读取大小，按 UTF-8 解码。

### `search_code`

采用大小写折叠（`casefold()`）进行**字面匹配**；限制项目扫描条目数、文件数、读取总字节、最大匹配数以及 snippet 长度。`max_matches` 的校验由 Pydantic Args Model 完成；不接受任意用户正则，避免 ReDoS 风险。

### `controlled_http_check`

Origin 由 State 指定，LLM 只能提供相对路径及 GET/HEAD 方法。禁用代理，禁止跳转，网络超时为 3 秒，GET 响应读取上限 64 KiB，超出时记录 `truncated`。

HTTP GET/HEAD 通常用于读取，但不能据此认为目标应用绝对没有副作用。工具应只指向自己拥有或明确授权的测试服务，特别是可能触发写操作的非规范 Web 应用。

### 本轮新增：`tests/test_http_loopback_integration.py`

采用 Python 标准库 `ThreadingHTTPServer` 在本机回环地址 `127.0.0.1` 临时启动 HTTP 服务，**没有访问公网**。验证：

1. GET `/health` 和 HEAD `/health` 确实到达本地服务；Observation 保存真实状态码，Finding/Evidence 均为空。
2. GET `/redirect` 只观察 302，不再请求 Location 指向的 `/should-not-be-requested`；直接检查服务器请求记录确认没有额外副作用。
3. GET `/large` 超过 64 KiB，结果正确标记 `truncated=True`，读取量不超过限制。
4. 对 `//evil.invalid/`、`/../secret`、`http://evil.invalid/` 等非法路径，Task FAILED 且本地服务的请求记录完全不增加。

这比仅做 `assert status_code == 200` 更能检验安全属性：不仅证明成功路径能运行，还证明拒绝路径**没有发生网络请求**。

## 7. Python 语法与架构复习

- `dict[str, Any]`：Python 泛型标注，表示键为字符串、值可以是任意类型；不等于允许任意工具参数。Tool Args Model 还要独立验证字段和取值。
- `Field(default_factory=dict)`：为每个对象新建字典，避免多个 Task 共享同一个 `{}`。
- `frozen=True`：禁止模型字段的普通重绑定；如果字段里存可变容器，仍需要额外深度冻结或不可变编码。
- `tuple[str, ...]`、`frozenset`：用于表示不可修改的依赖或允许集；设计上帮助固定审批绑定和权限配置。
- `try / except`：仅捕获预期权限/参数错误并映射为可观察失败；不要靠捕获 Agent 的 `TypeError` 猜测签名。
- `Mock.assert_not_called()`：检查危险分支没有调用工具，是安全测试中的副作用断言。
- 依赖注入：在 `main.py` 中先创建 ToolExecutor，再传入 Agent；把权限装配放到 Runtime 入口，不由 Planner 决定。
